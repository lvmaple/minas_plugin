# pcbackup — 小米智能存储「PC 备份」插件

把 **电脑上的目录** 增量备份到 **小米智能存储（NAS）**。插件按照《小米NAS插件开发规范》开发，
在米家 App / 桌面端的应用市场里打开使用。

## 功能

| 场景 | 行为 |
|---|---|
| PC 上新增的文件 | 上传到 NAS |
| PC 上修改过的文件（大小或修改时间变化） | 覆盖上传 |
| 未变化的文件 | 跳过（零流量） |
| **PC 上已删除的文件** | **NAS 端把对应备份文件改名为 `<原名>.del`**（数据保留，不真正删除） |

附加能力：

- 浏览器文件选择模式按 8 MiB 分块上传并保存本轮计划；取消或关闭后选择原目录，核对待传文件的路径、大小和修改时间，从 `.pcbp.part` 继续，不重新扫描或重传已完成文件
- 桌面端原生路径备份会保存本轮计划；中断后任务卡片提示「继续备份」，只核对待传文件，不重新遍历整个 PC 目录。完整的原生临时文件可直接在 NAS 上完成收尾；不完整的原生文件重新上传该文件
- 上传后保留文件原始修改时间（mtime），SMB 里看到的时间与 PC 一致
- 删除保护：删除量超过清单 20% 且 ≥10 个文件时需要勾选"强制执行"，防止选错目录导致大面积误标记
- 目录切换保护：换了目录名会先弹确认，确认后重建清单，旧文件**不会**被误标删除
- 文件复活：被标记 `.del` 的文件若在 PC 上重新出现，会重新上传为新文件，旧 `.del` 保留
- 排除规则（支持 `*` 通配，`node_modules/` 表示任意层级的同名目录）
- 新任务默认排除依赖和虚拟环境（如 `node_modules/`、`.venv/`）、开发缓存（如 `__pycache__/`、`.gradle/`）、测试报告与覆盖率产物（如 `test-results/`、`coverage/`）及 `*.pyc` 等生成文件。测试源码目录 `test/`、`tests/` 不在默认规则内
- 排除规则可在任务编辑页逐行修改；更新插件不会覆盖已有任务保存的规则。新增排除规则后，已备份的匹配文件会移出清单，NAS 上的文件默认保留，只有选择清理排除文件时才会删除
- 备份历史、备份文件在线浏览与下载
- 可在任务卡片删除任务；删除任务会移除配置和清单，NAS 上已备份的文件保留

## 工作原理

```
米家 App / 桌面端（Electron WebView）
  └─ 插件页面 src/ui（选目录 → 增量比对 → 上传）
       │  HTTPS /plugin/<uid>/pcbackup/api/...（nginx 反代）
       ▼
后端服务 src/files/httpd.py（NAS 上 systemd 常驻，127.0.0.1:9303）
  ├─ 清单库 etc/jobs/<id>/manifest.json（每个文件的大小+修改时间）
  ├─ 增量计划：比对「本次选择的文件」与「清单库」
  ├─ 上传落盘：原生临时文件 / 浏览器 xxx.pcbp.part → 原子改名为正式文件
  └─ 删除标记：正式文件 → <原名>.del
```

桌面端有原生桥接但没有 Node 文件读取能力时，使用 App 的 `upLoadToNas` 把文件传到用户数据目录内的独立临时路径，再用一个 `finalize` 请求完成收尾：校验大小、设置归属和修改时间、一次文件 `fsync`、直接原子改名为正式文件、追加清单。原生路径不再先生成 `.pcbp.part` 再调用 `commit`；浏览器分块和后端的 `complete → commit` 路径保留。

App 的 MOVE 失败时，只要原始 PUT 已完整落盘且收到终止回调，后端也可直接收尾。确认请求丢失时以同一标识重试，不会重新上传；文件已改名但尚未入账时，用改名前保存的文件身份补记清单。未确认结束的旧 PUT 使用独立标识重传，旧回调不能提交较新的上传或新一轮备份。上传前后都会核对 PC 文件大小及修改时间。

不同文件收尾可以并行；同一目标文件串行。任务编辑、重新扫描、删除和结束操作会等待正在执行的后端文件操作结束。取消会停止新请求并保留未完成计划，继续备份时跳过已提交文件。此版本没有引入批量提交、目录批量刷盘或日志刷盘队列；进程退出恢复测试不代表物理断电验证。

扫描和续传计划携带持久化代次标识。数据分块、提交、准备目录、准备原生上传、删除处理和结束请求均绑定发起时的计划；编辑目标、来源或排除规则及重新扫描后，旧请求返回 409，不能写入新目标。配置变更先撤销旧代次，再发布新配置；撤销写入失败不会发布新目标，配置发布失败则保留旧配置、拒绝旧计划，需重新扫描。页面遇到计划失效会停止派发后续文件并等待已发出的文件操作结束。升级后需刷新插件页面；未携带代次标识的旧页面请求会被拒绝。旧版续传记录仅在目标、排除规则及保存的 PC 来源完全一致时迁移并固定代次，来源缺失或不一致时要求重新扫描；不会删除已有分块或备份文件。

扫描、断点恢复和提交回包重试都会核对实际备份文件的大小及修改时间，容许 1ms 时间舍入差异；NAS 文件存在但属性不符时不能作为已完成文件跳过。不同任务的结束历史使用共享锁串行读写，避免互相覆盖。

整轮结束使用后台校验和短请求轮询。页面与黑色日志框在收到最终回执前显示「收尾校验中」，不会按已上传数量提前报告成功；单个控制请求仍有 60 秒超时，整轮物理校验不受该请求时限约束。收尾请求标识和结果保存在任务目录 `finish-request.json`，请求丢失后按同一标识重试，服务进程重启后查询可继续未完成收尾；成功记录不会重复校验或重复记历史。回执写入失败后，重新打开页面可仅凭持久化请求标识发起恢复，服务端使用原始统计和代次校验，不创建另一轮备份。全局历史仅保留最近 100 条；原记录被其他任务的历史挤出后，仍可用该任务持久化的最近结果核对运行及请求标识并恢复回执，不重新校验已完成文件、不重复记历史。读取大规模续传进度同样使用后台核对和轮询；续传文件打开、读取或解析失败会返回错误，仅文件不存在时表示没有续传记录。临时核对失败在返回错误后释放失败状态，线程启动失败则立即释放占位，后续请求可以重新执行核对。网络故障按连续次数限制，健康响应后清零；轮询断网后优先继续查询，服务端处理失败才重新受理。服务端失败预算在正常状态查询成功后清零，单次重新受理成功不清零；连续断网、网关非 JSON 错误和持续核对失败仍有限退出。

校验和排除文件清理期间可以取消：在文件之间检查取消，停止后续清理并保留续传记录及排除清单，继续时安全跳过已经删除的排除文件。清理结束后，在开始写入最终历史和任务结果前再次检查取消，并与取消接口同步决定；一旦进入最终结果提交阶段，取消接口会明确返回未接受取消，以最终回执为准。决策锁不跨越历史、配置的磁盘写入，状态查询可以继续返回。

续传核对期间仍使用独占许可，保证计划和清单一致。任务列表不会等待这次核对或繁忙的任务锁，而是返回临时摘要并显示「续传核对中」或「统计读取中」，不把临时的零计数显示为实际备份数量。续传查询与收尾查询使用各自的请求标识，重新打开任务可加入已有续传核对。

续传记录无法解析或格式不兼容时，普通续传仍返回错误；明确选择重新扫描后，先检查目录切换、路径和删除保护，再撤销旧计划代次，并将原记录原样隔离为任务目录内的 `pending-run.json.corrupt-<标识>`，随后创建新计划。已有备份文件和未完成分块保留。原生选择目录前更新来源时，损坏记录不会阻挡配置保存，但会撤销旧代次，原记录仍保留到重新扫描确认后再隔离。临时打开、读取故障不会按损坏记录跳过；代次写入、隔离或扫描线程启动失败后可以重试。

分块数据另以任务、来源、计划代次、运行标识和磁盘文件身份绑定；同一计划取消、重试和重启后可以继续。重新扫描、来源变化、身份记录缺失或分块被替换后，查询只报告可续传长度 0，不删除旧字节；首次从头上传时将旧分块及说明保存到备份目录的 `.pcbackup/partial-recovery/`，再写入新文件，不能把旧前缀与新来源的后缀拼接。身份记录读取失败可重试；未成功记录的字节不能作为可信偏移。旧版无身份记录的分块也按此规则保留副本并重新上传该文件。

目录选择、分批筛选和扫描请求均固定本次操作标识，旧结果不会覆盖新选择。保存来源时检查预期的旧来源和当前页面的选择顺序，即使重新选回原目录，迟到请求也不能撤销较新的选择；来源未变时不重写配置或撤销计划。上传期间重新选择不会改动正在使用的来源。文件大小和时间戳取自同一次属性读取，避免列目录后文件增长时仍按旧大小上传。拖拽读取任一文件或子目录失败时，停止整次比对并提示重试，不把读取失败当作文件已删除。成功读到的空目录及全部被排除的文件可以进入原有删除保护和清理流程。

浏览器模式在同一页面继续备份时，若收尾确认曾因断网失败，先以原请求标识和统计重试确认，再读取剩余计划；已经结束的计划转为重新比对，已提交文件自动跳过。取消或部分完成后的继续操作同样先刷新进度，不使用上传前缓存的旧文件列表。

原生文件的续传校验仅缓存运行标识，不保留整份文件列表。服务重启后首次访问读取一次已有计划，此后通过文件标识、大小和时间戳检测计划是否变化，不再逐文件解析大计划。新建或替换计划时直接更新缓存；重新扫描、修改任务、成功结束或删除任务时使缓存失效。取消继续保留当前计划与运行标识。

废弃原生上传采用延迟回收：替换 token 或删除任务前，先在插件数据目录 `native-retired/` 持久化归属记录；记录写入失败则保留原任务和原 token，允许重试。后台在服务启动后及每小时检查一次，只有废弃至少 7 天、暂存文件最近 7 天未写入、且不再被当前原生记录引用时，才回收对应 token 的 `.temp_upload_dir` 文件；删除前再次核对文件身份。记录读取或删除失败保留回收记录供下次重试。当前恢复仍需的暂存、已有备份、分块隔离副本和旧版失去归属记录的文件不参与回收。正常原生上传成功路径不增加回收记录或刷盘；普通增量修改中，旧上传已终止且没有暂存数据时也跳过登记。未终止的旧上传仍登记，保留迟到写入的回收能力。

PC 将目录改成同名文件时，计划记录需要保留的旧目录。删除标记完成后，先将仍存在的旧目录原子改名为唯一的 `<名称>.<标识>.del`，再上传新文件；已有 `.del` 和未管理的目录内容保留。目录内待清理的排除文件同时更新到保留路径，准备步骤可重试和重启恢复。普通文件无需这一步请求。

清理排除文件失败会返回错误并保留待清理记录及未完成计划，之后可重试；不会把未删除的文件报告为清理成功。

原生上传不会自动降级到 `getPcFileStream`：该接口不能定长读取、停止流或隔离文件事件。需要分块传输时，使用浏览器选择文件夹，或可用的 Node 定长读取。

目录准备每批最多处理 2000 个文件路径，同时执行最多 2 批，按已确认完成的批次累计进度。任何一批失败后停止派发新批次，等待已发出的批次结束；全部批次成功后才启动上传。黑色日志框显示任务名、当前阶段、各批次完成情况和累计处理数量，批次乱序完成也不会让进度倒退。

控制请求最多等待 60 秒，浏览器分块最多等待 5 分钟；原生单文件连续 2 分钟没有字节推进或总耗时超过 6 小时会请求停止并保留恢复信息。文件上传并发为 6，页面进度更新最多约每秒 5 次；目录进度每批确认后输出一条日志。

变更判定与 rsync 默认一致：**大小 + 修改时间（毫秒）**。
（浏览器安全策略限制，页面无法记住本地路径，所以每次备份都需要重新选择一次目录。）

## 部署

### 前置条件

- NAS 已开启 SSH，Windows 可 `ssh root@<NAS_IP>` 免密登录（工程里
  `xiaomi-storage-minas-tool` 有开 SSH 的脚本）
- 真机 UID：<NAS_UID> / IP：<NAS_IP>（可在命令行参数覆盖）

### 一键部署（Windows PowerShell）

```powershell
cd <PROJECT_DIR>\xiaomi-nas-plugin-pcbackup\deploy
.\package-and-upload.ps1                    # 默认 <NAS_IP> / uid <NAS_UID>
```

### 手动部署

```bash
# 1. 上传解压到 NAS /tmp/_pcbackup_pkg
scp pcbackup-plugin.zip root@<NAS_IP>:/tmp/
ssh root@<NAS_IP> "unzip -o /tmp/pcbackup-plugin.zip -d /tmp/_pcbackup_pkg"

# 2. 执行部署脚本（自动：备份 .list/nginx → 部署目录 → www 软链 → 注册 → systemd → nginx 注入）
ssh root@<NAS_IP> "sh /tmp/_pcbackup_pkg/deploy/deploy.sh <NAS_UID>"

# 3. 完全退出米家 App / 桌面端后重进（App 启动时才拉插件列表）
```

部署脚本会自动完成规范里所有关键步骤：www 软链指向 `src/ui`、图标放
`/data/plugin/www/icon/pcbackup.icon`、`.list` 的 `frontend.url` 用数组 + hash 路由、
nginx 规则插在 `location /plugin` **之前**，并带 `client_max_body_size 256m`
（分块上传必需）。

## 使用

1. 杀掉米家 App / 桌面端重进 → 应用市场 → **PC 备份**
2. 新建任务：起个名字、选 NAS 存放目录（如 `/nas/pool0/pcbackup/我的文档`）
3. 点「开始备份」→ 选择电脑上的文件夹 → 自动增量比对
4. 确认计划（上传 N / 跳过 M / 标记删除 K）→ 开始备份
5. 完成后可在「文件」里浏览、下载，在「历史」里查看每次备份结果

如果桌面端上传中断，重新打开插件，点击任务卡片的「继续备份」，再选择「继续上次备份」。这会继续上次确认的文件列表，并复用能够确认身份且已完整落盘的原生临时文件；中断期间新增或删除的文件，需要之后再选「重新扫描目录」执行新一轮备份。重新扫描会替换旧的续传记录。续传前会核对待传文件的大小和修改时间，文件已变化时应重新扫描。

## 安全说明

- 插件以 root 运行，后端做了严格的路径校验：拒绝绝对路径、`..` 穿越、反斜杠、
  控制字符，且任何已存在路径组件是符号链接时拒绝写入
- 备份目标目录限定在 `/nas/pool0/`、`/home/`、`/tmp/`、`/mnt/`、`/media/`、`/srv/` 下
- API 只监听 `127.0.0.1`，外部只能经 NAS 443（mTLS）的 nginx 反代访问
- 上传产物 chown 回插件用户（`u<uid>`），SMB 可正常访问
- 清理任务备份数据只允许删除该任务新建的目录；目录含其他备份任务时会拒绝。旧任务的目录默认保留，可手动清理。

## 重启持久化（重要！）

真机实测：**NAS 重启会清掉手动部署的插件**（开机时系统从 `/etc/config/plugin` 的 `ports` 表重建插件目录和 `.list`，不在表里的插件被丢弃）。deploy.sh 已内置三层保险：

| 层 | 机制 |
|---|---|
| ① | 端口注册进 `/etc/config/plugin` 与 `/data/etc/upper/config/plugin` 的 `ports` 表（让系统"认识"插件） |
| ② | 源码整体备份到 `/data/backup/plugins/pcbackup/`（/data 分区重启不丢） |
| ③ | `pcbackup-restore.service` 开机自愈：自动恢复插件目录、www 软链、图标、`.list` 注册、systemd 单元并启动服务、nginx 反代 |

即使极端情况下全部丢失，备份数据与清单也不受影响：
- 清单双写在备份数据目录（`<数据根>/.pcbackup/manifest.json`），插件目录被清时自动恢复
- 两份清单都没了也能靠"认领"（同名 + 大小 + 修改时间一致）从 NAS 现存文件重建

验证方式（不用真重启）：

```bash
# 在 NAS 上模拟清理后手动跑自愈脚本
rm -rf /home/u<NAS_UID>/plugin/pcbackup
sh /data/backup/plugins/pcbackup/restore.sh
```

## 常见问题

| 现象 | 原因 / 解决 |
|---|---|
| 上传报 413 | nginx 未注入 `client_max_body_size 256m`，重跑 deploy.sh 第 6 步 |
| 上传中途断开 | 正常，`.part` 会续传；再点一次备份即可 |
| 桌面端插件打不开 | 确认 `.list` 的 url 是数组且带 `#/`；改过 config/.list 必须杀 App 重进 |
| 页面没有显示新功能 | 检查 `index.html` 中脚本的 `?v=` 版本号；升级时同步改版本号强制刷新 |
| 想恢复被标记删除的文件 | 在「文件」里找到 `.del` 文件下载，去掉 `.del` 后缀即可 |
| 服务日志 | NAS 上 `/tmp/pcbackup/server.log` |
| 端口冲突 | 本插件用 9303（9301 sysmon / 9302 dockerctl），改端口需同步改 INFO、.list、control、nginx |

## 已知限制

- 不复制空目录结构；成功读取为空的原生目录或拖拽目录仍会同步旧文件的删除。浏览器文件选择器不暴露空目录名称时，请用拖拽目录或桌面原生选择
- PC 端的符号链接不跟随（以浏览器读取到的文件为准）
- 内容变化但大小和修改时间都没变的文件会被跳过（与 rsync 默认行为一致）
- 浏览器续传需用户重新选择原目录，并核对待传文件的路径、大小和修改时间；浏览器不提供绝对路径。免遍历选择目录仍依赖桌面 App 原生路径读取
- 原生上传目标需与用户数据目录位于同一文件系统；跨文件系统目标请使用浏览器选择文件夹
- 宿主 App 的原生上传接口没有公开的通用监听器清理接口；插件会释放自身的任务状态和定时器，晚到回调会被忽略。若旧版已造成宿主流事件积压，升级后需完全退出桌面 App 再打开
